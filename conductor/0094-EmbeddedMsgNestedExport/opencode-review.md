**Findings / blind spots:**

1. **`D-0069-embed-object` is not polish — it is the documented discovery mechanism, and the spec's own lock 3 mischaracterizes it.** MS-PST §2.4.6.2.2: "if the attachment is itself a message, the data is stored in **PidTagAttachDataObject**… the nid value of the PtypObject property structure (§2.3.3.5) is a subnode which is a fully formed message… not located in the NBT and do[es] not have a parent folder." §2.3.3.5: a PtypObject in a PC stores `dwValueHnid` → an 8-byte heap allocation `{Nid, ulSize}` pointing at the subnode. The writer's current layout places the nested message under the attach's subnode leaf but writes **no 0x3701 property at all** — writer_fidelity.rs:584-602 asserts the absence and comments "PidTagAttachDataObject (PtypObject) remains residual." That layout is discoverable only by lenient readers that scan the attach's subnode tree for NID_TYPE_MESSAGE — which is exactly what pst-reader's `resolve_embedded_from_attach_entry` does. **Consequence: DoD-1 "reopen shows nested message" will pass against our own reader while a spec-conformant MAPI client (Outlook) has no documented path to the nested message** — defeating the track's operator-fidelity purpose. And it is cheap: the 0x3701 prop-id constant already exists (production.rs:109), the nested subnode is already placed correctly, and `PcValue` just needs an `Object{nid, size}` variant writing the 8-byte heap struct with ptyp 0x000D (same machinery as `SubnodeString`). Recommend: fold D-0069-embed-object into 0094 Phase 2, have DoD-1's reopen resolve *via the 0x3701 property* (property-based resolution with scan fallback), and add one operator Outlook smoke on INC output to DoD-5. If excluded, the deferred entry must state the Outlook-open consequence explicitly — "residual polish" does not.
2. **The reader API is identity-shaped, not canonical-shaped — Phase 1 is materially larger than "wire the DTO through."** `EmbeddedIdentityFields` carries subject/sender/displays/full plain body/recipients/child-attach metadata, but **no HTML body, no `message_class`, no `message_id`, no `message_flags`, no delivery time** — all needed for a `WriteMessage` round-trip (nested PCs also need `PidTagMessageClass` present: §2.5.2.4 Get=PC). The main-path `read_message_properties`/`read_message_extract` are NBT-driven (`load_pc` with NBT lookup, message.rs:240) and cannot read nested NIDs. So Phase 1 is a bids-based full nested extract: refactor the main extract to accept `MessageNodeRef`/bids or extend embedded.rs with a full-field read **including an HTML byte budget** (nested HTML is the bulk of the ~645 KB average nest). Spec should also define the **nested-message-level fidelity contract** — which nested fields are Preserved vs dropped (HTML? flags? message_id?) — the locks only cover attach-level honesty.
3. **Depth-budget semantics: three constants, no single source of truth, and a reason-misclassification trap in DoD-3.** Writer default 3 / clamp [1,8]; reader identity-depth 3; engine hash-depth 3. If the extraction path enforces its own depth/byte budget and fails, the attach arrives with `embedded: None` → counted **`ATTACH_EMBEDDED_UNPARSED`, not `ATTACH_DEPTH_LIMIT`** — DoD-3's counter undercounts exactly the case it exists to measure. Spec should name the budget owner (propagate the writer constant into the extraction call), and require budget exhaustion to surface as a distinct materialize-side signal mapped to `ATTACH_DEPTH_LIMIT` (or a new `EMBEDDED_BUDGET` reason) rather than generic unreadable. Also note the risk table's "cycles" is malformed-input only — subnode containment is a strict tree in a well-formed PST; depth+byte budgets suffice.
4. **Parent identity stability is implied but not locked.** Tier-2 hash preimage is subject|submit|sender|body preview|attach name:size (hasher.rs:4) — an added `embedded` field perturbs nothing *if* filename/size stay source-derived. Lock 4 covers only the 0090 embedded hash; it should be generalized: *parent `content_hash` and `strong_content_hash` must be byte-identical with extraction on vs off*, with a regression test hashing the same fixture both ways. Otherwise unique-set selection shifts across versions and cross-run diffs explode.
5. **The DTO decision has unstated constraints.** `CanonicalMessage` requires `content_hash: [u8;32]`, `locus: MessageLocus` (folder path — nested messages have none), `fidelity`, `message_id_norm`, `edrm_mih_hex`; none exist naturally for nests. Options: synthesize (nested `content_hash` via 0090 `embedded-msg-hash/v1` is the natural fit; locus parent-relative) or a lighter `NestedCanonicalMessage` mapped to `WriteMessage` separately. Also: the field becomes visible to every consumer (EML pack, GUI, CSV, keep-set serde) — state explicitly that legacy EML export *ignores* it (scope §4 excludes EML but doesn't say "field present, path unchanged"), and add `skip_serializing_if` to keep serialized keep-sets from ballooning. Materialize-time RAM peak for parents with several ~645 KB nests is real — the lazy-extract-only-for-winners mitigation in the risk table is the right call; make it a Phase-0 lock, not a note.
6. **DoD-1's test does not exist today and must be written stronger than test 12.** Current coverage checks method/size/absence-of-0x3701-binary only; no test reopens and *resolves* a nested message from writer output. DoD-1 should require: resolve via 0x3701 (post finding 1), compare nested subject/sender/recipients/body against source, and assert `embedded_messages_written >= 1` *plus* `embedded_unparsed == 0` on the fully-parseable fixture.
7. Minor: scope item 1's "(and rfc822-as-embedded if already modeled)" is ambiguous — method-5 nests whose class is RFC822 vs by-value `.eml` attaches (method 1, mime `message/rfc822`); wiring the latter as nested would violate lock 3. Disambiguate in Phase 0. **Opportunities:**

- **One small primitive, two wins:** writing the 0x3701 PtypObject both completes D-0069 and lets pst-reader add property-based resolution (spec-conformant primary, subnode-scan fallback for legacy 0069-era output) — the reader stays compatible with both old and new writer output.
- Reuse `embedded-msg-hash/v1` as the nested `content_hash` — per-nest identity for free, enabling future nested-message dedupe/reporting without a new scheme.
- QC strata: add a has-method-5-attach / max-nest-depth candidate to `select_sample_indices` (the 0080 pattern) so every run exercises the nested path.
- Budget-aware extraction can stream child-attach bytes straight to the writer's `AttachStreamSource` (0069) instead of buffering whole nests — keeps the ~241 MB corpus out of RAM without new machinery.
