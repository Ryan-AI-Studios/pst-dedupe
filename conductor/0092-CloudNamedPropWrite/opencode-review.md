# opencode-review — 0092 CloudNamedPropWrite (spec/plan review, review only)

- **Series context / verdict summary:** see `../../opencode-review.md` — verdict: **Strongest spec; strengthen QC**.
- **Method:** code snapshot claims verified against `main` @ `c5437d0`; MS-OXCMSG / MS-PST / MAPI docs fetched 2026-08-24; no code edits made.

**Verified:** production writer NPMAP stub at `crates/pst-writer/src/production.rs:1271-1277` (empty PC via `build_pc_v2`); fixture writer stub at `lib.rs:1247-1253`; reader encode helpers exported (`crates/pst-reader/src/lib.rs:75-78`); reader NPMAP parse consumes three streams — GUID/entry/string — and ignores the MS-PST hash table (`named_prop.rs:145`).

**Findings / blind spots:**

1. **Spec citation error:** §2.2 says the production stub is `lib.rs ~1247` — that's the *fixture* writer. Production is `production.rs:1271`. The plan already says "inventory stub call sites (lib.rs fixture vs production.rs)" — fix the spec so Phase 0 starts from the right file.
2. **The allowlist question is already answered by MS-OXCMSG §2.2.2.9 (afByWebReference, 0x7):** "The PidTagAttachLongPathname property contains a fully qualified path identifying the attachment. The PidNameAttachmentProviderType defines the web service API manipulating the attachment." Combined with the PidTagAttachLongPathname docs (reference attachments set LongPathname; platforms set both pathname forms), the **minimal allowlist is exactly one string-named property: `PidNameAttachmentProviderType` in `PSETID_Attachment`** — the same entry 0084's reader already resolves (`NAME_ATTACHMENT_PROVIDER_TYPE` + `PSETID_ATTACHMENT`). The spec's "or equivalent / or documented cloud attachment property set" hedges can be resolved in Phase 0 with this citation; scope shrinks accordingly. The remaining judgment call is only whether to also carry `PidTagAttachPathname` (0x3708) alongside LongPathname for older-client tolerance — cheap, classic tags, no NPMAP cost.
3. **Reader round-trip is necessary but not sufficient — the NPMAP hash table is the risk.** MS-PST specifies a named-property-lookup-map **hash table** and a "Name-to-ID Map – minimum PST requirements" section. The current empty-PC stub passes reader + scanpst + 0080 attestation, so degenerate maps are evidently tolerated — but a *populated* map with no/invalid hash table is untested against Outlook. `NameIdMap::from_streams` ignores the hash table entirely, so "map parses with pst-reader NameIdMap" (DoD-1) cannot catch this. Recommend promoting scanpst-on-copy from a risk mitigation to a **DoD-level QC step**, and — since Outlook COM is declined (0080) — one human Outlook open attestation for a populated-map fixture via the existing `qc_attestation_v1` machinery.
4. **Mutual-bug risk in golden tests:** writer+reader round-trip can share a misunderstanding of the NPMAP HN layout. Phase 1's golden-bytes tests should include at least one fixture derived from a **real PST's** NPMAP bytes (operator-local, per evidence policy), not only self-generated expectations.
5. **NPID assignment determinism:** entries must get stable NPID (`0x8000 + index`) assignments referenced consistently from attach PCs. Lock assignment order (e.g., sorted allowlist order) in Phase 0 — this is the 0087 deterministic-key ethos applied to the map, and it makes diff-based QC tractable.
6. **Write-condition design (plan Phase 0 "always emit minimal NPMAP vs only when cloud attaches present"):** prefer *always emit when any allowlisted prop is used*, and emit no map otherwise (current behavior) — writing an always-present map changes every existing golden/QC digest for zero benefit on cloud-free exports.

**Strengths:** hardest fences are right (no hydrate, ledger URL mandatory, fail-closed fidelity contract, hard allowlist, never mutate sources); correct placement as the series' highest-risk/last track.

**Sources (accessed 2026-08-24):** MS-OXCMSG §2.2.2.9 PidTagAttachMethod; PidTagAttachLongPathname / PidTagAttachPathname canonical properties; MAPI "Opening an attachment"; MS-PST named property lookup map section set (incl. hash table, minimum PST requirements).
