# opencode-review — 0090 EmbeddedMsgContentHash (spec/plan review, review only)

- **Series context / verdict summary:** see `../../opencode-review.md` — verdict: **Re-baseline before start**.
- **Method:** code snapshot claims verified against `main` @ `c5437d0`; Relativity Server 2024 docs + MAPI/MS docs fetched 2026-08-24; no code edits made.

This is the spec needing the most rework before start.

**Findings / blind spots:**

1. **"Relativity-style" is a misattribution.** Verified from Relativity Server 2024 Processing docs: Relativity computes four *separate* hashes (Body, Header, Recipient, Attachment); the attachment hash "takes each SHA256 hash of each attachment and hashes the SHA256 hashes together"; embedded emails are **extracted as documents** ("If the email contains embedded electronic email data, the email data is also parsed and stored"), and deduplication "only applies to parent files; it doesn't apply to children." **No documented Relativity feature recursively hashes embedded message content into the parent's identity.** The spec's §2.4 preimage is a sound *project-invented* design, but labeling it "Relativity-style" invites operators to assume cross-tool dedupe parity that can never hold (different algorithm, different normalization, different embedded-email semantics). Recommend: rename in docs to something like "embedded-aware identity hash (`embedded-msg-hash/v1`), pst-dedup-specific, *inspired by* four-component email hash models," plus an explicit "this is not Relativity dedupe parity" line. Also document *why* recursive-hash-in-parent was chosen over Relativity's actual semantics (extraction/family — which this repo already models in the matter family graph), since that's the decision a reviewer will ask about.
2. **The core premise is wrong for `ATTACH_EMBEDDED_MSG`: embedded content is a subnode message object, not bytes.** `open_attachment_data` returns `PropertyNotFound` for embedded messages without binary (`crates/pst-reader/src/messaging/attachment.rs:475-476`; MAPI docs confirm: for ATTACH_EMBEDDED_MSG the data object commonly errors and the message must be opened as a subobject). Consequently, under `body-recip-attach` today, method-5 attaches hash as the **Choice B unread sentinel** (`hash_attachment_stream` marks unread on open failure, `crates/pst-dedup-cli/src/attach_content_hash.rs:127-129`) — not "raw attach-stream SHA-256" as the deferred entry and spec §2.1 claim. Computing §2.4's `body_hash`/`recipients_hash` (0082 recipient TC of the *embedded* message) requires parsing the attach subnode as a Message object — i.e., a **new, bounded pst-reader capability** that the spec simultaneously declares out of scope ("full recursive nested MAPI extract … D-0067-embedded-depth"). The spec must split the two cases:
   - (a) attach-by-value `.eml` (method 1 / `message/rfc822`): raw bytes exist (`eml_pack.rs:880-889` already labels them); a bounded rfc822 parse is feasible;
   - (b) `ATTACH_EMBEDDED_MSG` (method 5): needs submessage parse (subject/body/recipient table) under hard budgets.
   As written, DoD-1 is achievable only for case (a) — the higher-value case stays sentinel. This materially changes the estimate: it's reader work plus hasher work, not just hasher work.
3. **Identity/export divergence is unaddressed.** If identity splits on nested content while export still writes embedded messages as raw `message/rfc822` bytes (case a) or soft-skips/flags-unparsed (case b, `eml_pack.rs:861-871`), keep-set splits can occur between messages whose *exported artifacts* are identical — or fail to occur between byte-different wrappers with identical nested content. 0080's QC compares output vs source, not identity semantics. Add a DoD item or doc note tying the two: e.g., keep-set output must surface `embedded_message_unparsed` / depth-cap flags alongside the strong-identity level, so 0080 sampling can catch identity/export drift.
4. **Preimage underspecification:** `attachments_hash_32` needs (i) attach **ordering** rule (attach index order), (ii) treatment of inline-ignored attaches (0076 `ignore_inline_attachments` — otherwise two runs with different flags silently change embedded identity), (iii) pin `depth_u8` semantics (0 = outer?), and (iv) whether child embedded messages recurse or fall back to raw-blob/sentinel at cap (already flagged in §2.4 — keep, but decide in Phase 0, not during implementation). Also consider a *count* budget (max embedded parses per message/run) alongside depth/byte, consistent with existing `strong_hash_attach_max_attaches`.
5. **Snapshot error (shared with 0091):** the digest fill path lives in `crates/pst-dedup-cli/src/scan.rs:802-863` + `attach_content_hash.rs`, not "dedup-engine hasher/grouping." §8's `cargo test -p dedup-engine -- hasher/grouping` will not exercise the wiring that changes; verification must include `pst-dedup-cli`.

**Strengths worth keeping:** opt-in only, versioned domain-separated preimage, hard budgets with fail-closed sentinels, golden tests for nested-change-splits and cap honesty.

**Sources (accessed 2026-08-24):** Relativity Server 2024 Processing User Guide + Processing Console Guide (deduplication hash model); Microsoft Learn — MAPI "Opening an attachment" (ATTACH_EMBEDDED_MSG subobject semantics).
