**Findings / blind spots:**

1. **Phase 1 tests exercise the helper, not the wire-up.** `poly_crc_*` unit tests (plan Phase 1 rows 1–5) cover `poly_crc_risk_adjustment` directly; `export_risk_all_poly_inc_like_ok` etc. cover `compute_export_risk`. But nothing asserts the `ScanSummary.files → CrcSourceClass → ExportRiskInputs` mapping, and spec §8's verification commands are all `--lib`. Since a broken mapper (e.g. reading the wrong field or summing rates instead of raw counters) would silently reintroduce the lie with a green lib suite, add one integration test (the 0097-review pattern: build a synthetic dual-rate source in a fixture PST, or `assert` the mapper output on a `ScanResult`) — or at least a unit test on the mapper function. Non-blocking; the mapper is small.
2. **`export_oracle` escapes the new fields (deterministic tests still pass).** `compare_integrity_counters` (`export_oracle.rs:229-247`) compares an explicit pointer list that today ends at `/export_risk/level` + `/scan/block_crc_rate` + `/scan/block_crc_read_rate`. Since the oracle uses the exact pointer list (not whole-JSON equality), adding four fields does **not** break `compare_export_packs` — but the *reason* and attestation (`poly_class_crc_discounted`, `effective_block_crc_read_rate`) will be invisible to equivalence checks. If 0099 wants parity of its own behavior, extend the pointer list with `/export_risk/inputs/effective_block_crc_read_rate`, `.../poly_class_crc_discounted`, `.../discount_attach_stream_crc`, `.../poly_class_crc_sources`. The spec locks 5 ("raw telemetry never zeroed") makes them stable JSON keys, so the comparison is sound. Optional.
3. **Reasons vocabulary edge: `poly_class_crc_discounted` fires whenever the flag is set, even when the level is `not_export_ready` for a non-CRC reason.** Spec §3.5 says emit `poly_class_crc_discounted` whenever the flag is true; in a mixed localized job the flag is false, but in the "scan `not_export_ready` + all-poly" matrix row, `poly_class_crc_discounted` and `scan_recommendation=not_export_ready` coexist in `reasons`. That is honest (both are true) and the sort is stable; operators reading a single reason line may be briefly confused — the matrix row already documents the expectation, and the wizard banners on `level`. Acceptable; a one-line doc note ("flags can co-occur when a non-CRC gate fired") would close it.
4. **`discount_attach_stream_crc` vs. events that are *not* CRC-noisy per source.** The spec derives attach-CRC discount purely from source CRC classes (`crc_noisy && !poly_class_crc`). The writer's `attach_stream_crc_events` is a **job-level** sum across volumes (`unique_pst_cmd.rs:2591`); there is no per-source attach-counter attribution, so a job with one poly source + one clean source where the clean source's attaches hit *their own* StoreB stream CRC would be discounted wrongly. Spec §3.7 explicitly declined per-event attach CRC split ("job-level discount is fail-closed and enough for INC*") — the product decision is documented, so this is a known residual, not a hole. Record it in the review or deferred note so it's not re-litigated as a regression.
5. **Verification command scope (minor):** §8 runs `cargo test -p pst-dedup-cli` but not `cargo test -p dedup-engine` — the spec modifies only the CLI crate, so the engine is untouched, but the runbook's `export_risk` doc rows and the engine's `PreflightRecommendation` are composed. The repo's own `verify.commands` (AGENTS.md) run full-workspace clippy already. Add `cargo test -p dedup-engine` for belt-and-suspenders against the monotone-max assumption.
