# opencode-review — 0097 BodyCloudTruncationHonesty (spec/plan review, review only)

- **Verdict:** **Right scope, and the root cause is now provable from code — but the plan leaves the diagnosis and the A/B/C policy choice open when the code already answers both.** The 62 empty `BODY_CLOUD_LINK_TRUNCATED` rows are **window-hit markers, not lost links**: `truncated` is set unconditionally whenever a body surface exceeds 100k chars, regardless of whether any document-shaped candidate was actually dropped. The plan's Phase 0 "classify" step can be closed now and the policy locked to a concrete recommendation. The plan also misses three real honesty gaps in the same scanner: the 2048-char URL cap is **silent** (over-length document-shaped URLs are dropped with no marker at all), the window edge can produce **false-positive real rows** (bare URL cut mid-string that still ends with an extension), and the marker row's `link_index: 0` **collides** with a real link_index-0 row for the same message. None blocks Ready status; all are fixable in the plan.

**Verified (code, all confirmed):**

- **Root cause (high confidence):** `scan_body_cloud_links` sets `truncated = true` on window overflow **unconditionally** — `body_cloud_links.rs:90-93` (HTML) and `:100-103` (plain) — before any candidate is examined. The scanner's own test `body_window_100k_truncates_and_misses_past_window_url` (`:812-826`) asserts exactly this: `truncated` true with **zero** hits. So any message whose HTML *or* plain body exceeds 100k chars emits one empty marker row. Since plain often mirrors HTML (and both are scanned), a single long thread can fire the window twice. INC0102784's 62 rows are therefore "body > 100k", not "62 links dropped". The plan's handoff note ("do not treat empty truncated rows as proof of 62 SharePoint links") is now a proven fact, not a caution.
- **Window-hit is the only cause that can fire with zero hits.** The links/message cap sets `truncated` only when a *new* document-shaped candidate is actually dropped (`try_keep_candidate` `:270-280`, `collect_bare` `:207-222`, `more_document_candidates_beyond` `:228-260`) — correct semantics. The URL-length cap **never** sets `truncated`: `try_keep_candidate` `:283` silently returns on `chars().count() > MAX_URL_LEN`, and the SafeLinks nested target does the same at `:371-373`. So over-2048-char document-shaped URLs are dropped with **no marker at all** — an under-reporting honesty gap in the opposite direction that the spec's option (C) should cover.
- **Window-edge false positive (real, low probability):** `body_window_str` (`:127-134`) cuts at exactly 100k chars. `bare_url_re` (`:72`) needs no closing delimiter, so a bare URL straddling the boundary matches as a truncated prefix; if that prefix happens to end with an extension (e.g. `.../book.xls` cut from `.../book.xlsx?d=…`), `is_document_shaped_cloud` `ends_with` (`:494`) records a **garbage URL as a real `BODY_CLOUD_LINK` row**. hrefs are safe (the href regex requires a closing quote, so a cut href never matches). Fix is cheap: only accept URLs fully inside the window, or extend the window by `MAX_URL_LEN`.
- **Marker row shape:** `BodyCloudLinkRow::truncated_marker` (`unique_export_report.rs:1365-1384`) hardcodes `link_index: 0` and empty `cloud_url`/`url_source`. A message with ≥1 real hit *and* truncation emits a real row with `link_index: 0` **and** a marker row with `link_index: 0` — duplicate keys for any consumer keying on `(msg_nid, link_index)`. The `truncated` column is a row-type discriminator (real rows always `false`, `unique_pst_cmd.rs:2511`), not per-row info — worth documenting.
- **Summary counters:** `body_cloud_link_truncated_messages` increments on `p.body_cloud_truncated` (`unique_pst_cmd.rs:2517-2519`), i.e. "body exceeded 100k", but its doc comment says "body scan caps truncated additional candidates" (`unique_export_report.rs:671`) — inaccurate. `messages_with_body_cloud_links` / `body_cloud_links_total` count only real hits (`:2495-2500`) — consistent. All three are written-winner-only (the loop at `:2490+` is the write loop), matching real-row scope. Spec lock 2.4 (summary must match ledger semantics after fix) is the right constraint; the counter name should be reworded or the semantics fixed.
- **No upstream body cap:** reader reads `PID_TAG_BODY` / `PID_TAG_BODY_HTML` with no truncation (`message.rs:346-357`), so the full body reaches the scanner; the 100k window is the only gate.
- **Existing tests:** dedup-engine covers window-truncated-with-zero-hits (asserting the *current* buggy semantics, `:812-826`), max-links cap (`:758-769`), and URL-length silent skip (`:772-778`). The unique_pst integration test `body_cloud_links_unique_pst_csv_and_count` asserts `body_cloud_link_truncated_messages == 0` for a small body (`unique_pst.rs:2484-2489`) and query preservation — but **no test exercises a >100k body through the CLI**, and no test covers the marker row shape or the link_index collision.

**Findings / blind spots:**

1. **Phase 0's classification is answerable now — lock it in the spec.** From code: window-hit is the only cause that fires with zero hits; URL-length is silent; links/message fires only on real drops; window-edge false positives produce *real* rows, not empty truncated rows. The 62 INC0102784 rows are window-hit markers. The plan should record this as the diagnosis and pick the policy, not leave A/B/C open.
2. **Policy recommendation: C + A hybrid, not B.** Option B (suppress empty rows, rely on summary) hides the window event entirely and leaves the counter mislabeled. The honest fix is C: make `truncated` mean "document-shaped candidates were actually dropped" by rescanning the tail past the window (a cheap regex pass over the remainder — the same probe logic as `more_document_candidates_beyond` but over the un-windowed tail). When it does fire, emit **one** marker row per message (A) with a reason detail distinguishing window-drop vs cap-drop. This satisfies DoD-1 ("≤1 honest marker per message") and DoD-2, and kills the 62-row spam at the source (most >100k bodies have no cloud links in the tail).
3. **The silent 2048-char URL cap is an honesty gap the spec's option (C) should cover.** A real document-shaped SharePoint URL longer than 2048 chars (long paths + query) is dropped with no marker and no counter. Either (a) record a distinct reason row for over-length drops, or (b) explicitly document the cap as a known miss in the export docs (the runbook already lists caps at `docs/unique-pst-ediscovery-runbook.md:125`). DoD-1's "honest" framing should include under-reporting, not just the empty-row spam.
4. **Window-edge false positive (bare URL cut mid-string) needs a guard.** Cheap fix: only classify candidates whose match ends before the window boundary, or extend the window by `MAX_URL_LEN` before scanning. Add a unit test with a document-shaped URL straddling the 100k boundary.
5. **Marker `link_index: 0` collides with real rows.** Give the marker a distinct index (e.g. `u32::MAX`) or a separate `marker` column, and add a CLI test with a message that has both a real hit and truncation.
6. **§8 verification omits the scanner's crate.** The core fix is in `dedup-engine` (`body_cloud_links.rs`), but §8 only runs `cargo test -p pst-dedup-cli --test unique_pst` and `cargo clippy -p pst-dedup-cli`. Add `cargo test -p dedup-engine` (scanner unit tests) and `cargo clippy -p dedup-engine --all-targets -- -D warnings`. The ledger entity `crates/pst-dedup-cli` seeds the CLI, but the scanner edit lands in dedup-engine — note the cross-crate provenance in commit summaries.
7. **Docs/CHANGELOG (DoD-4) should describe marker semantics, not just caps.** `docs/unique-pst-export.md:560` and the runbook `:125` list caps but never explain what a `BODY_CLOUD_LINK_TRUNCATED` row means or that the summary counter counts window events. After the fix, document: marker = "document-shaped candidates were dropped past caps", real rows = kept hits with full query. CHANGELOG 0085 entry (`CHANGELOG.md:70`) should get a 0097 follow-up line.
8. **Minor:** the `truncated` CSV column is a row-type discriminator (real rows always `false`) — document it as such in the export docs so consumers don't read it as per-row truncation. Also, `body_cloud_link_truncated_messages` doc comment (`unique_export_report.rs:671`) must be corrected to match the fixed semantics.

**Opportunities:**

- **Reuse the existing probe for the tail rescan.** `more_document_candidates_beyond` (`:228-260`) already implements "are there document-shaped candidates beyond what we kept" — the fix needs the same logic over the *un-windowed* tail. Extract a shared `has_document_candidates(text, seen)` helper and call it on the remainder when the window fires; set `truncated` only if it returns true. Minimal diff, directly testable.
- **Add a `truncate_reason` column** (`window` | `max_links` | `url_len`) to the marker row so counsel can distinguish "body too long to scan fully" from "too many links" — this is the "clear reason detail" the spec's option (A) asks for, and it makes the summary counter honest by construction.
- **CLI integration test for the honest semantics:** build a source PST with a >100k body containing a document-shaped URL *past* the window (assert 1 marker row + 0 real rows) and one with a >100k body and no cloud links at all (assert 0 marker rows after the fix). The existing `body_cloud_links_unique_pst_csv_and_count` pattern (`unique_pst.rs:2400`) is the template.
