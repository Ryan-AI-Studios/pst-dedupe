**Findings / blind spots:**

1. **Phase 0's citation task can be closed now — pin it in the spec.** The exact anchors: property name string `"AttachmentPermissionType"`, property set PSETID_Attachment `{96357F7F-59E1-47D0-99A7-46515C183B54}` (MS-OXPROPS §2.371), type **PtypInteger32**, values 0/1/2 = None/View/Edit (MS-OXCMSG §2.2.2.28). The plan should record these as invariants the tests assert, not leave them as a to-verify item. Decide value handling: preserve any i32 as-is (open-world, matching the provider string's open handling) — do not reject out-of-range values; MAY-if-present means present-value-preserved, not present-value-validated.
2. **The change is 4 crates; the plan names 2.** Beyond pst-reader (NPID resolve + AttachmentInfo field) and dedup-engine (CanonicalAttachment field + `#[serde(default, skip_serializing_if)]` for keep-set JSON back-compat — older `keep_set_summary.json` must still load), the plan's own Phase 1 "stop hardcoding None" lands in pst-writer (production.rs:1217/1246), and the *actual* extract bridge is pst-dedup-cli `pst_materializer.rs:618` — a file the plan never mentions. Miss that mapping and DoD-1 silently fails (field populated nowhere). Ledger entity `crates/pst-reader` seeds only the first crate of four; either accept cross-crate provenance in the commit summaries or start against the crate with the most edits.
3. **QC compare surface (Phase 2) is unspecified and partially degraded.** The ProviderType QC compare lives in the payload-less cloud-pointer branch (unique_pst_qc.rs:1852-1882) fed by `MessageContentDetail.attaches` — a **positional 6-tuple** `(filename, size, mime, hash, provider, method)` that must grow a 7th element for permission. Two structural gaps to note in the plan: (a) the *persisted* digest path hardcodes provider empty ("content-digest path has no provider", unique_pst_qc.rs:1598) — permission QC will only work on the live-read path, so the DoD-1 test must exercise fresh source reads, not stale `content_digests_v1` rows; (b) the compare only fires for payload-less attaches — permission on a payload-bearing attach is never compared. Document both as known limits or fix while touching the code.
4. **Write-path gating decision is unstated.** Allowlisted named props are written only by `write_cloud_link_pointer_attach` (production.rs:3263-3281). A source attach carrying PermissionType but *not* classified cloud (payload present, or provider absent so `classify_attach_pc` stays Classic) will populate the canonical field and then drop it at write. Recommendation: extract unconditionally on PC presence (spec lock 1), write only on cloud-pointer rows (current behavior, defensible since MS-OXCMSG scopes these props to web-reference attachments), and word the contract row accordingly ("preserved on cloud pointer rows when source had it").
5. **Fixture bootstrapping risk (DoD-1).** No real corpus has PermissionType, so the round-trip fixture must be writer-generated: write source PST with `cloud_permission_type: Some(1)` → reader → canonical → writer → QC. That is a self-consistency test: a shared NPMAP-name/GUID mistake (writer and reader agreeing on a wrong string) passes round-trip but fails on real Outlook PSTs. Mitigate: unit-assert the exact spec constants (name string bytes, PSETID GUID bytes, PtypInteger32 tag) against the MS-OXPROPS/MS-OXCMSG values cited in finding 1, and keep the 0084-era NPMAP parse tests (which were built against the real stream format) as the external anchor.
6. **Identity-hash isolation must be stated as a lock.** The new field must not enter `attachment_meta_strings` (hasher.rs:443) or `attach_content_hash` inputs — doing so would change content hashes, silently re-grouping duplicates and invalidating existing indexes/keep-sets. Currently safe by construction; add one sentence to the spec locks (cheap insurance against an "obvious" refactor later).
7. **Verification commands omit two of the four touched crates' tests.** §8 runs `cargo test -p pst-writer -p pst-reader` but not `-p pst-dedup-cli` (materializer mapping + QC tests live there) nor `-p dedup-engine` (canonical serde round-trip test at keepset.rs:3491 is the pattern to extend). Clippy covers all four; the test list should too.
8. Minor: `PidNameAttachmentOriginalPermissionType` (MS-OXPROPS §2.370 / MS-OXCMSG §2.2.2.27, PtypInteger32, same value table) is unmentioned — add it to §4 Out of scope explicitly so "PermissionType" isn't ambiguously read as both.

**Opportunities:**

- **Refactor the attaches tuple into a struct while extending it.** `(String, u64, String, String, String, Option<i32>)` growing to 7 positional fields with mixed types is bug-prone (unique_pst_qc.rs already maps it positionally with `_` drops at 1593-1600 and 1827). A small `AttachDetail` struct makes the permission addition and any future prop additions safe. Same for the QC `OutAttachSlot` 5-tuple (unique_pst_qc.rs:1825).
- **Mirror the ProviderType contract row** (fidelity_contract.rs:232-236) with a `PidNameAttachmentPermissionType` Preserved row, so QC `classify` has a named row instead of falling through to the generic `cloud_modern_attachments` wording ("Permission when known" is currently aspirational — 0096 makes it true).
- **Add permission to the SoftSkipAttachRecord ledger** (keepset.rs:926-941 carries provider/url): counsel actionability — the permission value says what the recipient could do with the link, which matters for review workflows.
- **Resolve all cloud NPIDs in one pass**: `list_attachments_inner` already resolves provider once per list (attachment.rs:465); add permission (and later Url) beside it rather than per-attach.
- **Value-table constants** (`PERMISSION_NONE=0 / VIEW=1 / EDIT=2`) in pst-reader for readable tests and self-documenting fixtures, used by the 0092-style writer tests too.
- Timing: 0096 is last in Series N by design (0 INC* signal). If 0097 (BodyCloudTruncationHonesty) touches the same cloud-attach surfaces, consider extracting the shared NPID-resolution helpers first here to avoid double-churn.
