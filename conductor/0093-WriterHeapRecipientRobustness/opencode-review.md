**Findings / blind spots:**

1. **The 2048 threshold is a single-page workaround presented as a format necessity — and it deviates from the documented ≤3580 rule.** MS-PST §2.6.1.2.2 ("Allocating from the HN"): a heap allocation MUST fit a single block, **max 3580 bytes**; §2.6.2.3.2 ("Inserting into the PC"): variable-size data **≤3580 ⇒ HN allocation**, **>3580 ⇒ subnode** (NID in `dwValueHnid`). Two consequences the spec/plan never state: (a) the *per-value* 3580 limit is the format rule; the *aggregate page* overflow is purely this writer's single-page `HeapBuilder` — the format's own answer is **multi-block HN** ("When an HN no longer fits within a single data block, a data tree is created to span multiple data blocks", §2.3.1.6: HNHDR/HNPAGEHDR/HNBITMAPHDR), which is what real Outlook does. (b) Diverting values in the 2049–3580 band to subnodes is **off the documented layout pattern** — readers dispatch on NID-type bits (§2.2.2.1) so it plausibly works, but it is untested against Outlook/scanpst and the module doc's "inherent to the MS-PST format" framing overstates it. Phase 0 must make this an explicit decision — keep 2048 + divert (documented deviation + operator scanpst/Outlook smoke on a 2–3.5 KB-diverted fixture) vs. restore 3580 semantics with a multi-page HN — not inherit it silently from the uncommitted diff.
2. **A fixed per-value threshold cannot bound aggregate page usage — DoD-1's fixture is too weak.** The message PC carries six helper-eligible strings (MID, subject, sender email, DisplayTo/Cc/Bcc) plus `message_class` plus inline body (≤2048) and inline HTML (≤2048). Six 1.5–2 KB strings ≈ 9–12 KB > 8176: **the same hard-fail is still constructible**, and it fails inside `encode_pc_value`/`build_pc_v2` (`production.rs:3763-3767, 3787-3793`) after diversion decisions are already made — no retro-divert possible. The probe heap already built for MessageSize (`production.rs:3425-3427`) is the natural hook for an adaptive pass (on overflow, escalate the largest inline strings to subnodes and re-probe). DoD-1's test should be a message with **multiple** multi-KB strings, not one >2 KiB DisplayTo, or it proves the wrong invariant.
3. **The 48-row cap is not a bound either — it budgets rows, not bytes.** Each row heap-allocates 7–8 entries (display/addr-type/email/7-bit/record-key/entry-id/search-key + optional SMTP, `production.rs:4054-4064`); 48 rows with 100+ char display names ≈ 40–60 KB of strings — still overflow, still batch hard-fail. The INC corpus passing (48 kept) is empirical, not an invariant. Cap must be budget-aware (stop when projected heap usage crosses a threshold; report the *actual* kept count in the event) or catch-and-retry with fewer rows. Otherwise this track can be Complete and a different corpus re-trips the same abort.
4. **Same-class overflow on the attachment-table TC (NID 0x671) is out of scope and uncapped.** `build_attachment_table_tc` (`production.rs:3384-3396`, schema `:4539`) allocates one filename HID + row per attach with no cap and no byte budget — a message with ~100+ attaches or long filenames overflows the same single-page heap and hard-fails the batch. The spec should either scope the symmetric cap+honesty or spawn a named residual (`D-0093` sibling) — "out of scope" without a deferred entry is a silent known-unknown, the exact failure mode this repo's deferred discipline exists to prevent.
5. **Phase 2's contract mechanics are unstated and non-trivial.** `classify(name, present)` cannot distinguish cap-truncation from real loss — QC needs a writer-surfaced per-message truncate count (kept vs source) to classify `known_gap`. The wiring exists by precedent (`WriteCounters` capped event Vec + uncapped counter, `production.rs:671-677`); what's missing from the spec is (a) the decision of **contract version semantics** — mid-v1 meaning change of `recipient_table` vs a new entry (e.g. `recipient_table_rows` BestEffort, keeping `recipient_table` = "TC present & schema correct" Preserved) vs a v2 bump — and (b) the rule that the truncate event must carry per-class kept/dropped counts (To/Cc/Bcc), since truncation keeps the first 48 rows in source order and therefore **drops BCC first** when `--include-bcc-recipients` is on — consistent with BCC de-prioritization but must be explicit for counsel-facing reports.
6. **Option A is real writer-format work — the plan's B-first default is right, and the spec-scope split should say so with citations.** MS-PST confirms the Row Matrix may live in a **subnode** ("modifying subnode data, if the Row Matrix is stored in a subnode", §2.6.2.4.4; TCINFO `hnidRows`) and TC variable-sized data can live "in the heap or in a subnode" (§2.3.4.4.2). So A = rows-matrix-as-subnode + multi-block HN for the per-row string HIDs + RowIndex BTH growth — three mechanisms, one of which (multi-block HN) is *also* the principled fix for finding 1. Also note HID `hidIndex` is 11 bits (max 2047 allocations per heap) — a no-cap design must respect that too. Recommend Phase 0 records this sketch under `D-0093-recipient-tc-multipage` so the residual inherits the research even if B ships.
7. **`message_class` is named in D-0068-01 but not covered by the fix.** The deferred entry lists "subject/sender/display_to/message_class"; the uncommitted helper covers MID/subject/sender-email/Display* but `PID_TAG_MESSAGE_CLASS` is still pushed inline (`production.rs:3319`). Custom form classes (long dotted names / GUID-qualified) exist in the wild. Either route it through `push_string_prop` or document why it's excluded — as written, DoD-3's "narrow D-0068-01" would narrow it less than the deferred entry describes.
8. **Snapshot/hygiene nits.** (a) Spec §2.2 says the `lib.rs` diff is "fixture `build_pc_v2` if still needed" — the actual diff is better overflow diagnostics in `try_alloc` (the observability that produced the operator evidence); describe it, and note the fixture-path `build_bth` remains unchecked-by-design. (b) Untracked `crates/pst-reader/examples/probe_out.rs` (operator NPMAP probe: hardcoded `output/inc0102784-0092-full` path, `.expect`) **breaks `cargo fmt --all --check` today** and references operator-local evidence paths — plan Phase 0's "inventory uncommitted diff" must explicitly include it: delete, or move under `output/` per repo hygiene, or promote to a proper ignored example. DoD-4 cannot pass while it exists as-is. (c) §8 omits the CLI-side tests that Phase 2 (counter → report/QC wiring, contract entry) will touch — add the `unique_pst` report tests alongside `unique_pst_qc_0080`.

**Opportunities:**

- **One primitive, two payoffs:** multi-block HN (§2.3.1.6) is simultaneously the principled fix for the string-aggregate overflow (restores documented 3580 semantics) and half of Option A's recipient TC. Even if 0093 ships B, Phase 0 should cost it once so D-0093-recipient-tc-multipage and any string-deviation residual share one design.
- Budget-aware truncation makes the cap self-tuning and makes the WARN honest by construction (actual kept count + heap snapshot — the new `try_alloc` diagnostics already produce those numbers for free).
